# 选型草案（从零重写）

## 1. 对照玩法需求：先确定技术问题是什么

这是一个**本地单机策略游戏**，外壳可以接近 CK3，但核心体验不是“看完所有信息再做最优决策”，而是：

- 玩家作为河东节度使，在五代十国的混乱局势中生存。
- 情报不完整、可能过时、带有立场，甚至彼此冲突。
- 玩家不能靠一个“可信度 72%”之类的分数直接得到真假答案。
- 玩家要从来源、时间、覆盖范围、细节完整度、互相矛盾等线索中自己判断。
- 平时不是每秒手动点按钮，而是给部下设置常驻方针，让世界慢慢运转。
- 异常和到期结果进入侧边消息流；点开消息后可以选择是否暂停。
- 真正的危机必须强制暂停，普通消息不能打断玩家。
- 已知范围内达到精确门槛后，才允许触发需要玩家确认的强制停顿；迷雾外不能凭空产生精确警报。
- 探子、招募、花钱、暴露、局部补救都属于模拟规则的一部分。
- 故事由开局种子和压力规则涌现，不写死“第 N 天发生某剧情”。
- 默认界面是**地图司令部 + 侧边情报消息流**，不是案头卷宗应用。

因此，技术选型最看重的不是“能不能做一张地图”，而是：

1. 能否稳定驱动一个可暂停、可慢速挂机、可强制停机的世界时钟。
2. 能否把规则模拟、信息可见性和 UI 展示清楚分层。
3. 能否高效更新地图迷雾、已知范围和消息流。
4. 能否保证存档后规则状态可重放、可验证。
5. 能否让大量界面信息保持可读，而不是被传统游戏 UI 组件限制住。
6. LLM 出错或不可用时，游戏仍然能正常玩。

## 2. 客户端引擎与语言选型

### 2.1 推荐：Godot 4.x + C#

#### 玩法需求 → 技术结论

| 玩法需求 | 技术结论 |
|---|---|
| 默认壳是地图司令部，地图和侧边消息流同时存在 | Godot 的 2D 渲染、Canvas、Control UI 和场景系统足够直接，适合做地图与复杂侧栏并存的桌面游戏界面 |
| 地图需要显示领地、道路、势力边界、迷雾、已知范围和目标标记 | 2D 节点、CanvasItem、自定义绘制和纹理图层可以把地图显示拆成多个独立层，按需重绘 |
| 玩家可以随时暂停，点消息可选暂停，危机必须强制暂停 | 自己实现一个明确的 `WorldClock` 和暂停状态机即可，不把“暂停”交给引擎默认暂停机制就能避免规则层被 UI 意外绕过 |
| 平时时间慢走，部下按常驻方针自动工作 | Godot 的主循环适合驱动固定步长或可调速的模拟更新；方针执行可以在规则层批处理，不要求每个单位每帧运行 |
| 侧边消息流需要大量列表项、筛选、已读状态和双时间戳 | Godot 的 Control 系统能承载专用消息流组件；列表可以采用虚拟化、分页或按时间窗口加载 |
| 迷雾和已知信息不能泄露底层真相 | 客户端可以只持有“玩家可见状态”，模拟层输出经过可见性裁剪的 `PerceivedState`，避免 UI 直接访问完整世界状态 |
| 需要跨平台发行桌面单机游戏 | Godot 可以覆盖 Windows、macOS、Linux，发布流程相对简单 |
| 需要快速迭代玩法和 UI | C# 提供较好的类型约束、重构能力和测试体验；Godot 负责场景、输入、渲染和资源 |

#### 推荐的客户端分层

```text
Client
├── Presentation
│   ├── 地图司令部
│   ├── 侧边情报消息流
│   ├── 目标选择与确认
│   └── 危机暂停界面
├── Application
│   ├── 输入命令
│   ├── 暂停/继续/时间倍率
│   ├── 消息打开策略
│   └── 存档/读档协调
├── Simulation Adapter
│   ├── 提交玩家命令
│   ├── 接收模拟结果
│   └── 请求玩家可见状态
└── Rendering
    ├── 地图底图
    ├── 势力层
    ├── 已知范围层
    ├── 迷雾层
    └── 标记与路径层
```

#### 语言建议

- **客户端主语言：C#**
  - 规则数据、命令、事件、存档结构需要较强类型约束。
  - 状态机、序列化模型和测试更容易维护。
  - 面对“来源不同但内容相近”“事件版本变化”“信息可见性裁剪”等复杂数据，C# 的类型系统比动态脚本更稳妥。
- **GDScript：只用于少量场景胶水和编辑器内快速交互**
  - 不建议让核心规则同时分散在 C# 和 GDScript 中。
  - 核心模拟、消息生成、暂停条件和存档逻辑只保留一套实现。

#### 什么时候不选 Godot

以下情况成立时，才考虑换引擎：

- 团队明确要求极高质量的 3D 城市、角色或电影化演出。
- 目标平台主要是移动端，并且要深度依赖移动端原生支付、推送、后台能力。
- 团队已经有成熟的 Unity 或 Unreal 工具链，并且项目重点从策略信息界面转向 3D 表现。

这里推荐 Godot 的理由是**本玩法的 2D 地图、信息侧栏、暂停状态机和桌面单机定位**，不是任何既有项目资产。

### 2.2 真实备选一：Unity 6 + C#

#### 适合什么情况

如果团队需要以下能力，换 Unity 更合理：

- 计划做 2.5D 或 3D 地图。
- 需要大量成熟的地图、动画、粒子、输入和 UI 第三方插件。
- 团队有较强的 Unity 工程和美术生产经验。
- 后续可能扩展到主机、移动端，或需要更完整的商业发行工具链。

#### 对本玩法的优点

- C# 生态成熟，适合写规则层、命令系统、存档和测试。
- UI Toolkit 或 UGUI 都可以实现侧边消息流和复杂筛选界面。
- Tilemap、RenderTexture、Shader 和自定义渲染管线可以支持迷雾。
- Addressables 适合管理地图、头像、事件插图和语言资源。
- Profiler、Memory Profiler 等工具比较完整。

#### 代价

- 对本项目的 2D 地图和大量信息 UI 来说，Unity 的工程复杂度可能偏高。
- 需要严格限制 MonoBehaviour 直接承载规则，避免模拟状态散落在场景对象里。
- 迷雾、世界时钟和存档仍要自己设计，Unity 不会自动解决玩法一致性问题。

#### 只有在什么情况下才换

> 当项目明确需要 Unity 的跨平台、3D 表现、插件生态或团队生产管线时才换；仅仅因为“Unity 更大”不构成换用理由。

### 2.3 真实备选二：Bevy + Rust

#### 适合什么情况

如果团队更看重：

- 规则模拟的确定性和性能。
- 长期维护中的内存安全。
- 大量实体、地图节点和批量模拟。
- 愿意接受较高的引擎基础设施建设成本。

则可以选 **Bevy + Rust**，或者使用类似的原生游戏框架，例如 **Macroquad + Rust**、**SDL2/Raylib + Rust**。

#### 对本玩法的优点

- Rust 的类型系统适合表达命令、事件、状态变化和存档版本。
- ECS 适合管理势力、人物、军队、据点、探子和地图节点等实体。
- 规则层可以做成独立纯 Rust crate，便于单元测试、回放测试和批量模拟。
- 性能边界清晰，适合大规模时间推进。

#### 代价

- UI、编辑器、资源导入和发行工具链通常不如 Unity/Godot 省事。
- 侧边情报流这种复杂信息界面需要更多自建工作。
- 团队需要熟悉 Rust 的所有权、异步边界和 ECS 思维。
- 早期做玩法验证可能比 Godot 或 Unity 慢。

#### 只有在什么情况下才换

> 当模拟规模、确定性、长期并发模拟或团队 Rust 能力是第一优先级时才换；如果首要目标是尽快验证“地图司令部 + 消息流”的可玩性，不建议一开始选 Bevy。

### 2.4 真实备选三：Flutter + Dart，或类似跨端 UI 框架

可选方案包括：

- Flutter + Dart
- Qt/QML + C++
- Avalonia + C#
- React Native 不建议作为首选，但可以作为跨端界面备选

#### 适合什么情况

如果产品更像：

- 桌面端策略信息应用；
- 需要同时覆盖桌面、平板和移动端；
- 地图是低频交互的平面图，而不是复杂实时渲染；
- 侧边消息流、表格、筛选和无障碍是核心；
- 对游戏特效和高频地图动画要求不高；

那么 Flutter 或 Qt/QML 有现实价值。

#### 对本玩法的优点

- 复杂列表、筛选、文本排版和多语言 UI 方便。
- Flutter 的 widget 体系适合做消息流和信息面板。
- Qt/QML 适合桌面级工具风格界面和原生窗口能力。
- 如果未来要平板版本，跨端布局成本较低。

#### 代价

- 迷雾、地图图层、动画和高频标记更新需要自己做渲染优化。
- “游戏世界在慢慢跑、危机立即停”的循环需要自行建立可靠调度器。
- 输入、资源、音频、存档、帧率和游戏发行体验不如专门游戏引擎完整。
- 很容易做成“会动的管理后台”，而不是有游戏感的策略游戏。

#### 只有在什么情况下才换

> 当跨端信息界面、平板体验和业务式文本交互明显高于地图渲染与游戏表现时才换；如果桌面单机游戏体验是第一目标，仍优先选 Godot 或 Unity。

## 3. 规则与模拟层放在哪里

### 3.1 推荐：客户端进程内的独立 Simulation Core

推荐结构：

```text
Godot Client
├── UI / Rendering
├── Application Layer
└── Simulation Core
    ├── World State
    ├── World Clock
    ├── Orders / Policies
    ├── Information Model
    ├── Visibility Rules
    ├── Event Scheduler
    ├── Crisis Evaluator
    └── Save/Replay Serializer
```

这里的“客户端内”不等于“所有代码混在 UI 里”。规则层应当是一个**不依赖 Godot 节点、不直接读 UI 状态的独立模块**。

#### 玩法需求 → 技术结论

- 本地单机 → 不需要为每次时间推进支付网络往返。
- 玩家随时暂停 → 模拟推进可以在一个明确的调用点执行，不依赖后台服务是否响应。
- 危机强制暂停 → 模拟层可以直接返回 `PauseReason.Crisis`，由应用层切换暂停状态。
- 主动动作不设额度 → 本地命令执行简单直接，不需要服务器做配额和锁竞争。
- 消息流只显示玩家应知内容 → 模拟层能在同一处同时维护真实世界和玩家认知状态，但对外只返回裁剪结果。
- 开局种子和规则涌现 → 本地模拟容易实现确定性随机数、回放和测试。
- 单机离线 → 不依赖网络，LLM 不可用时也能继续游玩。

#### 必须坚持的边界

- UI 不能直接修改世界状态。
- UI 只能提交命令，例如：
  - `SetPolicy`
  - `RecruitScout`
  - `SpendFunds`
  - `InspectMessage`
  - `ConfirmTarget`
  - `Pause`
  - `Resume`
- 模拟层返回：
  - 状态变化；
  - 新消息；
  - 到期回报；
  - 可见性变化；
  - 强制暂停原因；
  - 可执行的后续命令。
- 每次模拟推进都带有：
  - 世界时间；
  - 随机数种子或随机数流位置；
  - 规则版本；
  - 命令序列号。

---

### 3.2 备选：本地独立进程

可以把 Simulation Core 做成独立本地进程，通过：

- stdin/stdout；
- local socket；
- named pipe；
- gRPC over localhost；
- 自定义二进制协议；

与 Godot 通信。

#### 适合什么情况

- 希望使用 Rust、C++ 或其他语言实现模拟层。
- 需要单独跑大量 AI 对局、平衡性模拟和回放。
- 希望模拟层未来能被编辑器、测试工具、批量模拟器共同调用。
- 规则层团队与客户端团队需要相对独立发布。

#### 代价

- 进程启动、崩溃恢复、版本匹配和通信协议都要维护。
- 存档、日志和错误定位更复杂。
- 玩家启动游戏时多一个进程，发行和杀毒软件兼容性需要验证。
- “危机强制暂停”必须保证通信延迟和异常不会让模拟继续偷偷推进。

#### 只有在什么情况下才换

> 当模拟层需要独立语言、独立工具链或大规模离线模拟时才换；如果团队规模小、目标是先把单机玩法做稳，不要为了“架构看起来独立”而拆进程。

---

### 3.3 不推荐作为首发：远程服务

远程服务可以用于：

- 账号系统；
- 云同步；
- 云端排行榜；
- 在线内容分发；
- LLM 代理；
- 崩溃和匿名遥测。

但不建议把核心规则模拟放到远程服务器。

#### 原因

- 单机游戏不应因网络抖动无法暂停或继续。
- 核心情报博弈需要可靠的本地状态和可重复存档。
- 网络服务会引入版本、延迟、成本、运维和隐私问题。
- LLM 请求失败不应该让游戏规则停摆。

## 4. LLM 调用边界

### 4.1 总原则

LLM 是**内容表现和有限的事件辅助工具**，不是裁判，不是规则引擎，也不是事实真相数据库。

规则层必须能够在没有 LLM 的情况下完整运行。

### 4.2 允许 LLM 做什么

适合由 LLM 处理的内容：

- 根据已经确定的事件事实，生成不同人物口吻的消息文本。
- 将结构化情报包装成符合人物身份的叙述。
- 对同一条已确定消息生成短标题、摘要和详细版本。
- 在事件结束后生成不改变事实的回顾性叙述。
- 生成风格化但受约束的传闻表达。
- 为已确定的政治关系、人物态度和来源背景生成有限文本变体。

输入给 LLM 的应该是经过裁剪的结构化数据，例如：

```text
事件类型：边境商路中断
消息来源：商队首领
来源状态：本人声称亲眼所见
发生时间：某年某月某日夜间
抵达时间：某年某月某日
可披露细节：道路北段无法通行
禁止披露：实际肇事者、未被玩家发现的兵力、隐藏规则数值
文本风格：谨慎、带地方口吻
```

### 4.3 禁止 LLM 做什么

LLM 不得：

- 决定事件是否真实。
- 给消息计算或展示“可信度分”。
- 直接修改金钱、兵力、领地、人物关系或战争结果。
- 读取并输出玩家尚未发现的迷雾外信息。
- 代替规则层判断是否触发危机强制暂停。
- 自由创造会影响规则的 NPC、军队或外交事实。
- 把“来源、完整度、矛盾、时间差”等线索压缩成一个真假结论。
- 直接把隐藏信息写进消息文案。
- 因为文案生成失败而阻塞时间推进。

特别是“可信度”不能变成以下任何形式：

- 可信度百分比；
- 星级；
- 颜色条；
- “大概率属实”标签；
- 用固定话术暗示游戏已经替玩家判真。

### 4.4 事件驱动，而不是每帧调用

LLM 调用只在这些时机发生：

1. 新消息需要生成展示文本时。
2. 玩家打开消息，需要补充长文本时。
3. 特定事件完成，需要生成回报时。
4. 玩家主动要求查看某个可生成的叙述版本时。

不要在每个时间 tick 调用 LLM，也不要让 LLM 参与每个 NPC 的日常决策。

建议采用：

```text
规则事件发生
→ 生成结构化消息事实
→ 立即进入消息流
→ 异步请求文案
→ 成功则替换展示文本
→ 失败则使用模板文本
```

### 4.5 降级方案必须是正式设计的一部分

LLM 不可用时：

- 消息仍然生成；
- 规则仍然推进；
- 危机仍然强制暂停；
- 玩家仍然可以查看来源、时间戳、完整度和矛盾关系；
- 使用模板化文本、短句和结构化字段代替长文案；
- 不显示“模型判断”或“生成失败导致信息不完整”的假借口。

推荐准备三层内容：

1. **结构化事实层**：永远存在，参与规则与存档。
2. **模板文案层**：本地可用，保证离线体验。
3. **LLM 风格层**：可选增强，不改变事实。

### 4.6 LLM 与隐私

- 默认不上传完整存档。
- 不上传地图外真相、完整 NPC 关系网和未发现事件。
- 只上传生成当前文案所需的最小字段。
- 提供关闭远程 LLM 的选项。
- 在本地单机模式下，不能因为不开启 LLM 就损失核心玩法。

## 5. 存档、状态与本地单机边界

### 5.1 推荐的存档内容

存档不是只存“当前日期和几项数值”，而应保存足以恢复信息博弈的状态：

- 游戏版本与规则版本；
- 开局种子；
- 当前世界时间；
- 随机数流位置；
- 玩家命令序列；
- 势力、人物、军队、据点和资源状态；
- 常驻方针及其生效时间；
- 事件调度队列；
- 已产生但尚未处理的异常；
- 消息流中的全部消息；
- 每条消息的世界发生时间和玩家收到时间；
- 来源身份及来源关系；
- 玩家已知范围、精确门槛和迷雾状态；
- 已发现的矛盾关系；
- 探子候选人及过期时间；
- 暴露状态和局部补救状态；
- 当前暂停原因；
- 已读、置顶、归档和筛选状态；
- LLM 文案缓存，但不能把缓存文案当成事实来源。

### 5.2 状态分层

建议区分三种状态：

#### A. 世界真相状态

规则层内部使用，包含所有 NPC、隐藏行动和未发现事件。

#### B. 玩家认知状态

玩家已经知道的内容，包括：

- 已见消息；
- 已知地理；
- 来源信息；
- 情报完整度；
- 已暴露矛盾；
- 过时信息；
- 精确门槛是否满足。

#### C. 展示状态

纯 UI 状态，包括：

- 当前地图缩放；
- 当前选中的目标；
- 消息筛选；
- 面板展开状态；
- 是否已读；
- 当前暂停界面。

保存时必须避免把展示状态误当成认知状态，更不能让加载 UI 状态绕过迷雾限制。

### 5.3 存档格式

建议：

- 逻辑数据使用版本化 JSON 或 MessagePack。
- 对大型历史消息和回放数据采用分块存储。
- 存档带校验和。
- 每次存档使用临时文件写入，再原子替换。
- 保留至少一个自动存档和多个手动存档。
- 读取旧版本时使用明确的迁移器，不在加载过程中隐式猜测字段含义。

### 5.4 确定性与回放

规则层应尽量做到：

```text
开局种子
+ 规则版本
+ 玩家命令序列
= 可重放的世界结果
```

这不是为了让玩家看到开发者调试信息，而是为了：

- 重现坏档；
- 测试危机暂停；
- 验证迷雾没有泄露；
- 检查事件是否因存档/读档改变；
- 做平衡性批量模拟。

### 5.5 本地单机边界

首发版本不需要：

- 账号系统；
- 云端权威存档；
- 实时联网；
- 在线排行榜；
- 远程规则判定；
- 强制联网；
- 为每个事件建服务器接口。

可以有可选的联网能力：

- LLM 文案；
- 崩溃报告；
- 可关闭的匿名统计；
- 可选云同步。

这些能力都不能成为核心玩法的单点依赖。

## 6. 地图迷雾与消息流性能架构要点

### 6.1 地图分层

地图至少拆成以下层：

1. 静态底图层：地形、河流、道路和地名。
2. 势力层：当前已知的势力边界和控制区域。
3. 已知范围层：玩家已经掌握的区域。
4. 迷雾层：未知区域遮罩。
5. 动态标记层：目标、军队、探子、危机和路线。
6. 交互高亮层：鼠标悬停、选中和可确认目标。

这样做的好处是：

- 消息到达时不必重绘整张地图。
- 只更新发生变化的图层。
- 迷雾可以按区域或网格增量更新。
- 地图外真相不会因为渲染对象存在而泄露给 UI。

### 6.2 迷雾的原则

- 渲染层只能拿到玩家可见数据。
- 未知区域不创建可被交互或调试读取的精确目标对象。
- 迷雾外不产生精确警报。
- 情报到达后，先更新玩家认知状态，再决定地图是否达到精确显示门槛。
- 已知范围扩大、精度提高和目标确认是不同状态，不能混为“亮了就知道”。

### 6.3 时间推进

不要让每个 NPC、每条道路和每个事件每帧执行完整逻辑。

建议：

- 使用固定逻辑步长；
- 世界时间慢速推进时按批次处理；
- 远离玩家关注范围的对象采用聚合计算；
- 只有到达事件时间点时才唤醒相关规则；
- 时间倍率变化只改变调度频率，不改变规则语义；
- 暂停时停止所有会改变世界状态的逻辑；
- 异步 LLM 返回只能更新展示缓存，不能偷偷推进世界时间。

### 6.4 危机暂停

危机判断属于规则层，不属于 UI 猜测。

规则层每次推进后返回：

```text
SimulationResult
├── state_changes
├── new_messages
├── visibility_changes
├── due_reports
└── pause_requests
```

其中 `pause_requests` 至少区分：

- 强制暂停：危机、已知范围内达到精确门槛等；
- 建议暂停：点开消息后可选暂停；
- 普通消息：不暂停；
- 玩家主动暂停。

UI 可以展示理由，但不能自行决定把普通消息升级成强制暂停。

### 6.5 消息流性能

消息流容易成为性能和可读性瓶颈，建议：

- 使用虚拟列表，只创建当前可见行。
- 列表项先展示轻量摘要，打开后再加载长文本。
- 结构化字段和文案分离。
- 消息按世界时间、抵达时间和紧急程度建立索引。
- 双时间戳始终可见，不依赖展开详情才显示。
- 消息去重必须保留“重复抵达”本身的情报意义，不能简单按文本去重。
- LLM 文案缓存按消息事实版本缓存。
- 筛选、归档和已读标记只改变展示状态，不修改消息事实。
- 大量历史消息采用分页、时间窗口或归档分区。

### 6.6 性能预算建议

在立项阶段就定下可测指标，而不是等卡顿后再优化：

- 世界模拟推进一次的最大耗时；
- 危机判定延迟；
- 地图增量更新耗时；
- 消息流滚动帧率；
- 读档时间；
- 自动存档时间；
- 最大消息数量；
- 最大已知地图节点数量；
- 最长单局世界时间；
- LLM 请求超时后的降级时间。

## 7. 推荐栈一句话总表

> **Godot 4.x + C# 客户端，内置一个与 UI 解耦的确定性 Simulation Core，使用本地版本化存档和事件驱动消息系统；LLM 只负责受约束的文案增强，规则、迷雾、暂停和核心情报逻辑全部离线可运行。**

| 层 | 推荐 |
|---|---|
| 客户端引擎 | Godot 4.x |
| 客户端语言 | C# |
| UI | Godot Control，地图与 UI 分层 |
| 规则模拟 | 客户端内独立 Simulation Core |
| 时间系统 | 固定逻辑步长 + 可调慢速推进 + 强制暂停状态机 |
| 随机性 | 带种子的确定性随机数 |
| 地图 | 分层 2D 地图 + 增量迷雾遮罩 |
| 消息流 | 虚拟列表 + 结构化事实与文案分离 |
| 存档 | 版本化 JSON/MessagePack + 原子写入 + 迁移器 |
| LLM | 事件驱动、最小上下文、可选增强、模板降级 |
| 网络 | 核心玩法不依赖网络 |
| 测试 | 规则单元测试、回放测试、迷雾泄露测试、存档往返测试 |

## 8. 主要风险

### 8.1 “信息不完整”最后变成了换皮的可信度系统

**风险：**

开发过程中很容易加上百分比、星级、颜色和“可靠/不可靠”标签，最后玩家仍然是在看系统答案，而不是自己判断。

**控制办法：**

- 禁止任何统一真假分。
- 每条消息只展示来源、时间、覆盖范围、细节完整度、互相矛盾和来源关系。
- 测试用例明确检查：相同事实不能被一个分数直接排序成真假。

### 8.2 强制暂停规则互相打架

**风险：**

普通消息、到期回报、已知范围变化和危机都触发暂停，玩家会觉得游戏不断被打断；或者反过来，危机没有及时停住。

**控制办法：**

- 所有暂停请求统一进入规则层的暂停分类器。
- 明确“危机”“精确门槛”“可选暂停”“普通消息”的优先级。
- 对每种暂停原因做自动化回放测试。
- 游戏设置中只允许关闭普通提示，不能关闭硬性危机暂停。

### 8.3 LLM 泄露迷雾外真相

**风险：**

把完整世界状态发送给 LLM，再要求它“写得像情报”，很容易把玩家不该知道的信息写进文案。

**控制办法：**

- LLM 输入必须经过玩家可见性裁剪。
- 规则事实和可展示字段分开。
- 对生成结果做敏感字段检查。
- 生成失败时使用模板，不重新发送完整上下文。
- 开发阶段加入“迷雾泄露测试”。

### 8.4 规则层和 UI 层互相污染

**风险：**

为了快速做功能，把“点击按钮就改数值”“打开消息就标记事实已确认”等逻辑直接写在 UI 回调里，后续无法验证和回放。

**控制办法：**

- UI 只能发命令。
- 所有状态变化必须由 Simulation Core 产生。
- 每个命令有输入、结果和错误原因。
- 禁止 UI 直接访问世界真相状态。

### 8.5 模拟规模增长后时间推进变慢

**风险：**

五代十国势力、人物、军队、探子和消息越来越多，时间一走就需要遍历所有对象。

**控制办法：**

- 事件队列代替每帧遍历。
- 远处对象采用聚合模拟。
- 先定义性能预算。
- 用最坏情况存档做基准测试。
- 不为了“看起来实时”而让所有 NPC 每帧运行。

### 8.6 存档读档改变了情报结果

**风险：**

随机数状态、异步文案、事件队列或版本迁移处理不严谨，导致读档后世界走向变化，玩家失去信任。

**控制办法：**

- 保存随机数流位置或命令回放信息。
- 规则事实先落盘，LLM 文案单独缓存。
- 自动做“推进—存档—读档—继续推进”的一致性测试。
- 存档记录规则版本，不允许无提示地用新规则解释旧状态。

### 8.7 地图做得很漂亮，但消息流不可用

**风险：**

玩家每天面对大量消息，不知道哪些是新信息、哪些是旧信息、哪些相互矛盾，最后体验变成阅读负担。

**控制办法：**

- 消息流先做交互原型，再做完整地图美术。
- 双时间戳、来源、影响范围和矛盾关系必须有稳定的信息层级。
- 支持按异常、到期、来源、地区和未处理状态筛选。
- 不用颜色单独表达重要信息，要提供文字和结构化标记。

### 8.8 过早拆成本地服务或远程服务

**风险：**

把单机模拟拆成服务后，开发精力转向通信、部署和错误恢复，而不是玩法。

**控制办法：**

- 首发坚持客户端内独立 Simulation Core。
- 只有出现明确的语言隔离、大规模模拟或工具复用需求时才拆本地进程。
- 远程服务只承载可选能力。
