# 3D 引擎选型补篇（从零立论）

## 结论先说

对于 wdsg 当前已经拍板的玩法，**首发不值得默认上 3D**。

这不是因为 3D 做不了策略游戏，而是因为 wdsg 的核心卖点不是“在一个漂亮的三维世界里走动”，而是：

- 玩家只能依据不完整、过时、可能带立场的情报做决定；
- 平时挂机，异常消息才打断；
- 危机发生时强制暂停，但玩家仍只能依据已知情报下令；
- 地图是证据板，不是每天反复浏览的主界面；
- 故事主要由开局种子和压力规则涌现，而不是按天播放固定剧情。

这些内容首先需要**模拟可信、信息表达清楚、暂停和消息流可靠**。3D 可以增强氛围，但不会自动增强“情报不完整”和“政治博弈”。如果 3D 让地图更漂亮，却让消息、来源、矛盾和玩家决策更难读，那就是给核心玩法添成本，不是添价值。

默认排序如下：

1. **仍然推荐 Godot 4.x + C# 的 2D 首发**；
2. 如果已经拍板必须做 3D，**首选 Unity**；
3. **Godot 4 3D 是小团队低成本的次选**，但要接受工具和美术管线不如 Unity 完整；
4. **Bevy 适合有 Rust 能力、愿意自建工具的技术团队**，不适合作为 wdsg 的稳妥首发；
5. **Unreal 不推荐**，除非项目已经明确变成高规格 3D 历史演出产品，并且有相应的美术、技术美术和 C++/Blueprint 团队。

## 1. wdsg 是否值得上 3D

### 1.1 3D 能带来什么真实收益

3D 的收益主要在“氛围”和“空间感”，不是在模拟本身。

对 wdsg 有价值的 3D 增益包括：

#### 一、让“河东节度使”更像一个实际存在的权力中心

玩家可以在地图司令部中看到：

- 山河、城池、关隘和道路的层次；
- 城池规模、地形险要和边境方向；
- 旗帜、烽火、驿站、军营等具有时代感的视觉符号；
- 雾气、阴天、夜色、风雪等反映局势压力的环境变化。

这能让“我在经营一个真实的边镇”更有感觉。

#### 二、让情报的“来源”和“局限”更有表现空间

例如：

- 已控制地区显示得清楚，远方只显示模糊地形；
- 亲眼确认过的城池与探子报告的城池使用不同的视觉表现；
- 过时情报保留旧标记，但在地图上出现时间痕迹；
- 矛盾消息不通过“可信度分数”表达，而是通过互相冲突的旗号、路线、时间和报告来源呈现；
- 敌军没有被发现时，地图不渲染一个玩家不应该知道的红色单位。

这些表现如果做得好，能把“地图是证据板”变得更直观。

#### 三、强化危机暂停的戏剧性

危机强制暂停时，可以有：

- 镜头缓慢转向已经知道的危机区域；
- 烽火、急报、城门关闭等低频环境变化；
- 侧栏消息明确写出“为什么现在停下来”；
- 玩家在地图上查看现有证据，再回到情报流下令。

但要注意：这些都是**表现层**。真正决定玩家是否感到公平的，仍然是消息内容、暂停理由和可见信息边界。

#### 四、为后期演出留下空间

如果未来要做：

- 重要人物在城中会面；
- 使者抵达、探子被捕、军队经过关隘；
- 一次关键谈判或背叛的短演出；
- 地图上的局部战事、围城和撤退；
- 不同季节和政局压力下的司令部变化；

3D 会比纯 2D 更容易形成“可以观看的场面”。

### 1.2 3D 会增加什么成本

#### 一、美术产能会明显增加

2D 地图上的一个城池，可能是一个图标、一组描边和几种状态。

3D 地图上的一个城池，往往至少需要考虑：

- 地形模型；
- 城墙、建筑、道路、桥梁；
- 材质和纹理；
- 不同距离的 LOD；
- 昼夜与天气；
- 遮挡关系；
- 选中、已知、过期、矛盾、受威胁等状态；
- 摄像机不同角度下是否仍然可读；
- 资产命名、导入、碰撞、灯光和性能。

地图上的城池一多，内容团队面对的就不是“画几百个图标”，而是“生产、维护和验证几百组空间资产”。

#### 二、3D 资产管线会吃掉工期

小团队通常低估以下工作：

- Blender 或其他 DCC 工具的建模规范；
- 贴图尺寸和材质标准；
- 导出、导入和重新导入；
- 骨骼、动画、粒子与特效；
- 引擎内 Prefab/Scene 的组织；
- 版本控制下的二进制资产冲突；
- 美术资源替换后的性能回归；
- 不同显卡和分辨率下的显示问题。

如果团队没有成熟的 3D 技术美术和资源管线，3D 很容易变成“程序在等资源，美术在补管线，制作人在等第一个可玩的版本”。

#### 三、地图和 UI 的可读性更难保证

wdsg 不是一款让玩家欣赏风景的游戏。玩家需要快速回答：

- 哪些地方是已知的？
- 哪些信息来自谁？
- 哪些报告已经过期？
- 哪些消息互相矛盾？
- 哪些目标是当前可以合法下令的？
- 为什么游戏强制暂停？
- 我是不是被系统偷偷告诉了不该知道的事情？

3D 地图会引入：

- 摄像机角度造成的遮挡；
- 地形和建筑遮住标记；
- 透视导致远处信息缩小；
- 雾效同时遮住景观和关键证据；
- 镜头移动让玩家失去空间参照；
- 图标、线条和文字在不同距离下变得拥挤；
- 侧栏与地图争夺注意力。

因此，3D 版本仍然必须保留一套**强制可读的抽象地图层**。如果最后玩家主要看的是正交投影、平面颜色、图标和侧栏，那么 3D 可能只剩下一个昂贵的背景。

#### 四、暂停和挂机并不会因为 3D 变简单

wdsg 的时间规则有明确区别：

- 平时时间慢走；
- 部下按照常驻方针自动工作；
- 普通消息可以关闭；
- 危机必须强制暂停，不能关闭；
- 玩家可以随时自愿暂停；
- 危机暂停和自愿暂停不是一回事；
- 玩家可选择继续挂机；
- 主动动作不设额度。

3D 引擎可以暂停渲染、动画和物理，但**不能替团队决定游戏模拟如何暂停**。仍然要明确：

- 哪些系统跟随游戏时间；
- 哪些界面动画跟随真实时间；
- 消息触发是在 tick 前还是 tick 后；
- 危机在多个事件同时发生时如何合并；
- 暂停瞬间是否允许完成当前命令；
- 继续挂机后是否一次性结算大量时间；
- 存档是在危机触发前、触发后还是玩家下令后生成；
- 3D 动画、粒子、音频和模拟时钟是否会互相错位。

3D 只会让这些问题多出渲染、动画和物理方面的边界情况。

#### 五、性能风险不主要来自“多几个模型”

策略游戏常见的性能问题是：

- 大量单位、城池和消息状态持续更新；
- UI 重新布局；
- 地图标记和连线批量重建；
- 路径、视野、迷雾和区域状态频繁刷新；
- 长时间挂机后一次性处理大量事件；
- 存档和读档时序列化过多状态；
- 3D 场景中的阴影、透明雾、后处理和粒子持续运行。

尤其是“平时挂机”意味着玩家可能让游戏运行很久。即使画面看起来不复杂，也需要确保：

- 非可见对象不无意义地逐帧更新；
- 模拟 tick 和渲染帧解耦；
- 迷雾不每帧重算；
- 消息流不会因为重复状态变化持续制造 UI 工作；
- 危机暂停后不再继续推进隐藏模拟。

#### 六、团队技能结构会被迫改变

2D 策略游戏的核心团队可以主要由：

- 游戏设计；
- 客户端程序；
- UI/UX；
- 数据和模拟；
- 叙事与内容。

3D 版本通常还需要稳定覆盖：

- 3D 环境美术；
- 技术美术；
- 材质与 shader；
- 灯光和后处理；
- 动画；
- 资源技术管线；
- 3D 性能优化；
- 摄像机和空间交互设计。

如果这些能力不是团队现成具备的，3D 的成本不是“多写一点代码”，而是新增一条生产线。

### 1.3 什么情况下 3D 才划算

满足下面多数条件时，3D 才有机会划算：

1. **3D 演出本身是产品卖点**，而不是“看起来更高级”；
2. 玩家需要频繁观察空间关系，且空间关系直接影响决策；
3. 地形、距离、遮挡、路线和视线是核心机制，而不是装饰；
4. 团队已经有稳定的 3D 美术和技术美术能力；
5. 有可复用的资产来源，并且授权、风格和质量可接受；
6. 有明确的低配目标、画面预算和性能测试设备；
7. UI 仍然能够在 3D 场景上清楚呈现来源、完整度和矛盾；
8. 3D 不会推迟第一个可验证的信息博弈原型；
9. 制作人愿意把地图、司令部和演出范围限制在一个可控规模；
10. 团队明确接受“3D 版本可能比 2D 版本晚很多，但玩法不一定更多”。

如果只满足“我们希望截图更好看”，不满足以上条件，就不该为首发上 3D。

## 2. 3D 引擎对比

### 2.1 总览

| 引擎 | 授权与成本 | 小团队上手 | 策略地图与 UI | 挂机/暂停与桌面单机 | 总体判断 |
|---|---|---:|---:|---:|---|
| Unreal Engine | 引擎免费起步，但有商业条款、版税/授权边界和较重的硬件、资产成本 | 较难 | 能做，但明显偏重 | 能做，桌面发行成熟 | 不推荐作为 wdsg 默认选择 |
| Unity | 商业授权规则相对成熟，需持续关注席位、收入门槛和平台条款 | 较容易 | 很适合，工具和资产最多 | 成熟 | 3D 分支首选 |
| Godot 4 3D | MIT 许可，无引擎版税；商业工具和资产需自行承担 | 中等 | 能做，UI 和 玩法层合适 | 桌面发行可行 | 低成本次选 |
| Bevy | MIT/Apache-2.0 生态，软件许可成本低；人力成本可能很高 | Rust 团队较容易，否则较难 | 可定制，但大量工具要自己造 | 可做，但工程基础需自建 | 不适合稳妥首发 |
| CryEngine | 商业条款、生态和人才供给不如主流选择 | 较难 | 没有明显优势 | 可做 | 不建议考虑 |

下面按 wdsg 的实际需求展开。

---

### 2.2 Unreal Engine

#### 成本

Unreal Engine 的软件入口成本不一定是最高的，但总成本通常最高。

需要考虑：

- 商业授权和收入条款；
- 可能涉及的版税或定制授权；
- 更高的硬件和测试设备要求；
- 大量 3D 资产、材质、灯光和技术美术投入；
- C++、Blueprint、Build、Cook、Packaging 等完整工具链的学习成本；
- 团队需要花时间理解引擎庞大的默认能力和项目组织方式。

具体授权门槛和商业条款会随时间、产品类型和发行方式变化，立项时必须以官方当前条款为准，不能只根据网上旧文章拍板。

#### 团队技能匹配

Unreal 更适合：

- 有 C++ 能力的中大型团队；
- 有成熟 Blueprint 规范的团队；
- 有专职技术美术、关卡、美术管线和性能人员的团队；
- 追求高规格实时演出、环境和镜头表现的项目。

小团队不是不能用，但很容易出现“引擎能力远大于项目需求”的情况。团队会花很多时间处理：

- 模块和插件边界；
- 资源烘焙与打包；
- 材质、光照和后处理；
- Actor、组件和世界管理；
- 编辑器工具与资产规范；
- 不同平台上的包体和性能。

#### 对策略地图、迷雾和密集 UI 的适配

Unreal 完全可以实现：

- 正交或透视策略地图；
- 分层地形；
- 迷雾和区域遮罩；
- 大量地图标记；
- 复杂的侧边消息流；
- 角色和场景演出；
- 事件暂停和单机存档。

问题不在“能不能做”，而在“是否值得用它做”。

Unreal 的强项是高质量实时 3D 场景、灯光、材质、动画和大型世界。wdsg 的强项需求却是：

- 证据状态管理；
- 信息可见性边界；
- 消息流和危机解释；
- 可测试的模拟；
- 长时间挂机；
- 大量文本和 UI 交互。

Unreal 能提供前一类能力，但后面这类能力仍然要团队自己搭建。它不会自动让情报 UI 更好，也不会自动解决迷雾公平性。

还有一个实际风险：高质量 3D 效果会诱使团队不断加内容，导致项目从“策略司令部”膨胀成“可自由漫游的历史世界”。这会直接冲击范围控制。

#### 暂停、挂机和桌面单机

Unreal 的桌面发行和暂停能力成熟，做单机游戏没有根本障碍。

但是应主动避免把游戏模拟绑在：

- 渲染帧；
- 物理帧；
- 角色动画；
- 粒子系统；
- 世界流式加载。

wdsg 应该有独立的模拟时钟和事件队列。渲染只是模拟状态的一个观察者。否则在暂停、加速、读档、回放和长时间挂机时，很容易出现状态不同步。

#### 推荐判断

**不推荐作为 wdsg 的默认 3D 引擎。**

只有在以下情况才考虑 Unreal：

- 项目已经明确要做高规格 3D 历史演出；
- 3D 场景和镜头是发行卖点；
- 团队有 Unreal 经验；
- 已经有专职技术美术和 3D 资产管线；
- 预算能承受较长的前期制作；
- 制作人愿意严格限制模拟规模和演出范围。

否则，Unreal 的优点会变成额外负担。

### 2.3 Unity

#### 成本

Unity 的主要优势是成熟、普及和完整的中间层工具，而不是“完全免费”。

需要考虑：

- 当前版本的 Personal、Pro 或其他商业授权规则；
- 团队席位成本；
- Asset Store、插件、字体、音频和美术资源费用；
- 某些第三方工具的订阅或版本兼容成本；
- Unity 版本升级带来的迁移和回归成本；
- 具体商业条款可能变化，立项时应查官方当前政策。

Unity 曾经引发过 Runtime Fee 相关争议，后来政策方向发生调整。结论不是“永远没有费用”，而是：**不要把任何旧的 Unity 费用文章当作当前合同依据**。应在项目启动时锁定编辑器版本、授权类型和发行条款，并记录在制作决策中。

#### 团队技能匹配

Unity 对小型和中型团队比较友好：

- C# 人才多；
- 3D 教程和社区资源丰富；
- Asset Store 选择多；
- 编辑器扩展成熟；
- UI、输入、场景、Prefab 和资源管理都有大量现成经验；
- 外包和招聘相对容易。

它也适合大团队，但大团队需要自己建立：

- 代码架构；
- Addressables 或资源加载规范；
- Scene 和 Prefab 规则；
- UI 性能规范；
- 包管理和版本锁定；
- 编辑器工具；
- 美术导入和验证流水线。

Unity 不会自动保证项目质量，但它给团队提供的可组合工具比较多。

#### 对策略地图、迷雾和密集 UI 的适配

Unity 对 wdsg 的适配度是四个候选里最均衡的。

可以较自然地组合：

- 3D 地形和正交摄像机；
- 2D UI 和 3D 世界；
- Canvas、UI Toolkit 或混合方案；
- 地图上的标记、连线和区域覆盖；
- Shader 或材质实现的局部迷雾；
- 可切换的抽象地图和演出地图；
- 角色、使者、军队和城池的轻量演出；
- C# 模拟层、事件队列和存档系统。

Unity 的重要价值不是“它能做出最漂亮的画面”，而是它允许团队把 wdsg 拆成比较清楚的层：

1. 独立的游戏模拟和情报模型；
2. 3D 地图表现；
3. 2D/屏幕空间情报 UI；
4. 资源与演出层；
5. 桌面输入、存档和发行层。

对于迷雾，需要特别注意不要直接把物理视线系统当成信息规则。wdsg 的“知道什么”来自情报模型，不一定等于摄像机当前看到了什么。Unity 能提供渲染遮罩和视野效果，但“玩家是否有资格看到这个事实”必须由游戏规则决定。

#### 暂停、挂机和桌面单机

Unity 做桌面单机发行成熟，暂停、时间缩放、场景切换和存档都有大量实践。

但仍应自己定义：

- `GameTime` 与真实时间的关系；
- 平时速度、暂停和危机暂停的状态机；
- 模拟 tick；
- 消息触发顺序；
- 自动方针执行顺序；
- 危机的合并和去重；
- 读档后是否重新触发危机；
- UI 动画是否在游戏暂停时继续播放；
- 音频、粒子和镜头演出如何响应暂停。

不要简单地把全局 `timeScale` 设为 0 就认为“暂停完成”。wdsg 的暂停是玩法规则，必须让玩家知道暂停原因，也必须保证模拟、消息流和命令确认的一致性。

#### 推荐判断

**如果团队已经拍板坚持 3D，Unity 是首选。**

理由是：

- 3D 能力足够；
- C# 与原有主荐方向相近；
- UI、编辑器和资产生态完整；
- 小团队比较容易找到人；
- 桌面单机发行成熟；
- 可以把 3D 限制为表现层，而不必让整个模拟依赖 3D 世界；
- 后期从抽象地图扩展到有限的 3D 演出比较现实。

Unity 的前提是锁定版本、减少插件数量、尽早建立资源规范，不要把项目变成 Asset Store 拼装工程。

---

### 2.4 Godot 4 3D

#### 成本

Godot 的核心优势是许可简单：

- 引擎本身采用宽松的开源许可；
- 没有按收入收取的引擎版税；
- 不需要为引擎席位付费；
- 可以查看和修改引擎源码；
- 桌面单机发行不需要向 Godot 交产品分成。

但“引擎免费”不等于“项目免费”。仍然要支付：

- 团队学习成本；
- 3D 资产和 DCC 工具成本；
- 自建编辑器工具的时间；
- 可能购买的插件和第三方服务；
- 招聘和培训成本；
- 遇到引擎缺口时自己解决问题的成本。

如果项目使用 Godot 4.x + C#，还要提前验证目标平台的 .NET 导出、CI、调试和打包流程。不要只在开发机上成功运行，就默认最终桌面发行没有问题。

#### 团队技能匹配

Godot 4 适合：

- 熟悉 Godot 节点、场景和信号的团队；
- C# 或 GDScript 能力较强的小团队；
- 愿意控制项目规模的独立开发团队；
- 希望降低引擎授权和商业条款风险的团队。

相较 Unity，Godot 的 3D 生态、现成中间件和大规模项目经验较少。团队可能需要自己补齐：

- 资源检查工具；
- 复杂地图编辑器；
- 批量导入和验证；
- 大量标记的渲染策略；
- 特定的后处理；
- 3D 美术管线；
- 性能剖析和跨平台验证流程。

#### 对策略地图、迷雾和密集 UI 的适配

Godot 4 其实很适合做“3D 场景 + 2D UI”的策略壳：

- 场景树和节点结构直观；
- Control UI 适合做侧栏和消息流；
- 2D/3D 场景可以组合；
- 自定义渲染和 shader 有足够空间；
- 小规模地图、城池和演出不难实现；
- 引擎本身不会强迫团队采用开放世界式架构。

它尤其适合以下 3D 方案：

- 正交或近似正交的地图；
- 低多边形、绘本式或版画式视觉；
- 地图作为平面证据板，3D 只提供地形起伏和氛围；
- 少量重要城池和人物做局部演出；
- 侧栏承担主要信息阅读；
- 迷雾更多是规则层和图层遮罩，而不是复杂的实时体积雾。

它不适合被期待为“用较少工程成本替代 Unreal 的高规格 3D 管线”。如果项目要大量角色动画、复杂地形流式加载、非常高质量的光照和成熟商业插件，Godot 的自建成本会快速上升。

#### 暂停、挂机和桌面单机

Godot 可以很好地承载单机策略的时间模型：

- 游戏逻辑可以独立于渲染；
- 场景树可以承载地图和 UI；
- 桌面导出路径清晰；
- 存档、输入和窗口管理都可自行控制。

但仍然要自己处理：

- SceneTree 暂停与模拟时钟的边界；
- 处理暂停时哪些节点继续运行；
- UI 消息是否继续响应；
- 3D 动画和粒子是否停止；
- 加速挂机时的批量结算；
- 迷雾层是否在暂停期间被错误刷新；
- C# 导出和目标平台运行时的版本一致性。

#### 推荐判断

**Godot 4 3D 是低成本、可控范围下的次选。**

它适合这样的 3D wdsg：

- 团队本来就熟悉 Godot；
- 视觉方向是克制、抽象、低多边形或插画化；
- 不追求大规模 3D 世界；
- 3D 主要服务于地图氛围和有限演出；
- 团队愿意自己补少量工具；
- 仍然坚持让模拟层、情报层和 UI 层保持清晰。

如果团队已经因为 2D 主荐选择了 Godot，那么转为 Godot 4 3D 的迁移成本会低于换到另一个引擎。但这不代表应当为了“已经选了 Godot”就强行做 3D。**低授权成本不能抵消 3D 内容生产成本。**

---

### 2.5 Bevy

#### 成本

Bevy 的引擎许可成本很低，生态主要基于 Rust 和开源组件。真正的成本来自人力：

- Rust 学习和招聘成本；
- 引擎 API 与生态变化；
- 自己搭建编辑器和工作流；
- 自己选择 UI、资产、场景、动画、存档和调试方案；
- 自己维护项目级基础设施；
- 长期跟随版本升级。

如果团队本来就是 Rust 工程团队，成本判断会不同。如果团队主要是 C#、GDScript 或传统游戏开发背景，Bevy 的“免费”可能只是把费用换成了开发时间。

#### 团队技能匹配

Bevy 适合：

- Rust 能力强；
- 喜欢 ECS；
- 有引擎或工具开发经验；
- 能接受自己组装技术栈；
- 项目有较强的模拟、批处理或数据驱动需求；
- 团队把技术探索本身视为项目目标的一部分。

它不适合：

- 希望快速完成可玩原型；
- 依赖成熟编辑器让非程序成员配置内容；
- 需要大量现成的商业 3D 资产工具；
- 团队没有专人维护引擎层；
- 首发时间和风险都比较紧。

#### 对策略地图、迷雾和密集 UI 的适配

从架构角度，Bevy 的 ECS 很适合表达：

- 大量城池、人物、部下和方针；
- 事件驱动的情报系统；
- 可批量处理的模拟 tick；
- 独立的可见性组件；
- 数据驱动的状态变化；
- 长时间挂机中的批量结算。

但是“适合表达”不等于“马上能交付”。

wdsg 还需要：

- 地图编辑和内容配置；
- 消息流 UI；
- 富文本和文本本地化；
- 迷雾与标记渲染；
- 资产预览；
- 调试和回放；
- 存档兼容；
- 美术与程序之间的交接工具。

这些工作很多需要团队自己决定方案并持续维护。对于一个核心风险在玩法和内容、而不是引擎技术的项目，这种投入通常不划算。

#### 暂停、挂机和桌面单机

Bevy 可以做出可靠的独立模拟时钟，也可以做桌面单机发行。但可靠性来自团队自己的架构：

- 使用明确的模拟阶段；
- 将游戏时间与真实时间分开；
- 定义暂停状态和事件提交点；
- 做好确定性或至少可重放的事件处理；
- 处理系统调度顺序；
- 对长时间挂机和批量事件做性能测试。

Bevy 不会替团队自动提供一套成熟的策略游戏时间系统。

#### 推荐判断

**不推荐作为 wdsg 的首发 3D 引擎。**

只有在以下情况下才值得考虑：

- 团队已经熟练使用 Rust 和 ECS；
- 有人愿意长期维护引擎层；
- 模拟规模或定制化需求确实需要这种自由度；
- 项目时间允许先做技术原型；
- 团队明确把工具建设纳入预算。

否则，Bevy 会把本应花在情报博弈和内容验证上的时间，转移到“把游戏做出来所需的基础设施”上。

---

### 2.6 CryEngine 及其他引擎

CryEngine 的渲染和大型环境能力有价值，但对 wdsg 没有明显的独特优势：

- 它不能替代情报模型和 UI 架构；
- 小团队人才和教程供给不如 Unity、Godot；
- 生态和中间件选择较窄；
- 授权和商业条款需要单独核实；
- 3D 资产管线仍然要自己承担；
- 采用它不会减少策略模拟和信息设计的工作。

同样，不建议为了“看起来更专业”选择一个团队不熟悉的专用引擎。除非已经有非常具体的技术原因，例如团队拥有现成的 CryEngine 项目和人员，否则它不进入 wdsg 的候选主名单。

## 3. 推荐与不推荐

### 3.1 默认推荐：继续 2D Godot 4.x + C#

这仍是 wdsg 的主推荐。

原因不是 2D 更便宜这么简单，而是它更直接服务于核心验证：

- 消息流是否让玩家愿意读；
- 来源、完整度、矛盾是否能被理解；
- 危机强制暂停是否公平；
- 玩家是否会因为信息不完整而做出有意义的判断；
- 自动方针和主动下令是否形成合理分工；
- 地图是否真的是证据板，而不是一个需要反复操作的菜单；
- 故事涌现是否比固定剧情更有趣。

这些问题应该先被验证。3D 不应成为验证它们的前置条件。

### 3.2 如果团队坚持 3D：首选 Unity

Unity 是最平衡的 3D 分支选择：

- 有足够成熟的 3D 工具；
- C# 与主荐方向连续；
- UI 和编辑器生态适合密集策略界面；
- 桌面单机发行路径成熟；
- 可以将 3D 限制为表现层；
- 方便引入有限的城池、人物和事件演出；
- 小团队比较容易找到外援和资产。

建议采用“抽象地图优先、3D 演出可插拔”的方案，而不是一开始就做一个完整可漫游的 3D 世界。

### 3.3 次选：Godot 4 3D

如果团队已经深度熟悉 Godot，且视觉方向是克制的策略地图，Godot 4 3D 可以成立。

适合的边界是：

- 小规模地图；
- 正交视角；
- 低多边形或风格化资源；
- 2D UI 占主要阅读面积；
- 3D 只做地形、气氛和少量重点演出；
- 不依赖大量商业级 3D 工具。

不适合的边界是：

- 复杂开放世界；
- 高规格写实光照；
- 大量角色动画；
- 复杂流式加载；
- 需要成熟商业插件解决大部分问题。

### 3.4 不推荐：Unreal 作为 wdsg 默认引擎

**坚决不该仅因为“3D 就应该用 Unreal”而选 Unreal。**

对 wdsg 来说，Unreal 的主要风险是：

- 引擎能力过剩；
- 3D 资产和技术美术成本过高；
- 容易把范围推向高规格演出；
- UI 和信息模拟仍需自行建设；
- 小团队缺少相应经验时，排查成本高；
- 3D 画面很容易挤压核心玩法的开发预算。

如果项目最终被重新定义为“以历史场景演出为核心的高规格 3D 产品”，再重新评估 Unreal；在当前玩法事实下，不应把它当默认选择。

### 3.5 不推荐：Bevy 作为稳妥首发

Bevy 并不是能力不足，而是它要求团队承担太多基础设施责任。

wdsg 当前更需要：

- 快速验证信息博弈；
- 可靠的暂停和存档；
- 可编辑的内容工具；
- 密集 UI 的快速迭代；
- 低风险的桌面发行。

如果团队不是 Rust/ECS/引擎工具方向，Bevy 会放大项目风险。

---

## 4. 与 2D Godot + C# 主荐怎么并存

### 4.1 首发 2D 后加 3D，还是一开始就 3D

默认建议：

> **先用 2D 兑现信息博弈，再决定是否加 3D 表现；不要一开始就把整个项目押在 3D 上。**

这里的“先 2D”不是做一个以后必然废弃的临时 Demo，而是先交付一套具有正式结构的玩法垂直切片：

- 独立的模拟时钟；
- 常驻方针；
- 消息流；
- 普通提示和危机强制暂停；
- 情报来源、完整度、矛盾线索；
- 探子招募、花费、暴露和假情报；
- 地图证据板；
- 存档和读档；
- 开局种子与压力规则；
- 一轮完整的挂机—消息—危机—下令—后果循环。

如果这套循环本身不好玩，3D 只会让问题更昂贵。

### 4.2 什么可以复用

只要从第一天就分层，2D 版本中的大量核心内容可以复用到 3D：

#### 可以直接复用或高度复用

- 游戏时间和暂停状态机；
- 事件队列；
- 部下常驻方针；
- 主动命令；
- 情报来源模型；
- 信息完整度模型；
- 矛盾和过期处理；
- 探子系统；
- 危机生成规则；
- 故事压力规则；
- 存档格式；
- 数据表和配置；
- 消息流的内容模型；
- 测试用例和模拟回放；
- 胜负和失败条件；
- 统计、日志和调试工具。

这些属于游戏的“真相层”和“模拟层”，不应依赖某个具体渲染引擎或地图表现。

#### 可以部分复用

- 城池、道路、区域和边界数据；
- 地图坐标；
- 目标选择规则；
- 迷雾的状态数据；
- 图标、标记和消息的语义；
- UI 文案和交互流程。

它们需要从平面绘制适配到 3D 投影、空间标记和镜头系统，但语义不应改变。

### 4.3 什么不能直接复用

#### 不能直接复用 2D 的视觉布局

2D 中一个固定位置的侧栏、连线和城池标签，到了 3D 需要重新处理：

- 镜头缩放；
- 遮挡；
- 透视；
- 屏幕空间与世界空间；
- 标记聚合；
- 高度和地形；
- 选中状态；
- 镜头跳转；
- 低分辨率下的可读性。

#### 不能把 2D 迷雾简单变成 3D 雾气

3D 雾气只能表达“看不清”，不能完整表达：

- 玩家从哪个来源知道某件事；
- 情报是何时获得的；
- 报告是否完整；
- 两个来源是否矛盾；
- 玩家是否已经知道某个目标存在；
- 游戏是否有意让目标保持未知。

因此，3D 迷雾至少要分成两层：

1. **规则层可见性**：玩家是否拥有这条事实；
2. **表现层雾效**：这条事实在地图上以什么清晰度显示。

规则层必须是权威来源，表现层不能反过来泄露规则层信息。

### 4.4 双轨开发的真实成本

“2D 和 3D 都支持”听起来很灵活，实际上很容易变成两套产品。

双轨成本通常包括：

- 两套地图表现；
- 两套镜头和导航；
- 两套迷雾渲染；
- 两套标记和连线；
- 两套性能预算；
- 两套截图、教程和 QA；
- 资产和 UI 的适配；
- 设计师需要同时维护两个版本的可读性；
- 每个情报状态都要检查两种表现是否泄露信息；
- 2D 和 3D 的输入方式可能产生不同的玩家行为。

因此，不建议把“2D 模式”和“3D 模式”都当成首发完整功能。

更可行的方式是：

- 模拟层只有一套；
- 情报层只有一套；
- 消息流 UI 只有一套主要实现；
- 2D 地图是首发主视图；
- 3D 只作为后期可替换的地图表现或重点演出；
- 不承诺 2D/3D 两种模式在首发同时完整支持。

### 4.5 推荐的分阶段路径

#### 阶段一：2D 信息博弈垂直切片

目标不是做临时假画面，而是验证：

- 挂机是否有节奏；
- 消息是否值得点开；
- 危机暂停是否能解释清楚；
- 迷雾是否让玩家感到“未知”，而不是感到“系统在耍我”；
- 错误情报是否能形成有意义的后果；
- 方针和主动动作是否互补；
- 玩家是否愿意持续进行下一轮。

#### 阶段二：2D 正式化与数据层固化

在核心循环成立后：

- 固化模拟数据结构；
- 固化存档版本；
- 固化事件日志；
- 固化消息和情报状态；
- 建立回放与测试；
- 将地图表现、UI 表现和模拟规则明确分层。

#### 阶段三：做一个有限 3D 试片

不要先做全地图。只做一个小范围试片：

- 一座核心城；
- 两三个邻接区域；
- 一条边境路线；
- 一次探子回报；
- 一次危机暂停；
- 一组矛盾情报；
- 完整的侧栏消息流；
- 低配设备上的性能测试。

试片要回答的不是“3D 好不好看”，而是：

1. 情报仍然清楚吗？
2. 地图仍然是证据板吗？
3. 玩家能否理解自己不知道什么？
4. 3D 是否增加了决策感，而不只是增加了镜头操作？
5. 3D 的美术产能是否能覆盖整个游戏？
6. 3D 是否把工期推到无法接受？

#### 阶段四：只增加有明确收益的 3D

通过试片后，再选择少量高价值场景：

- 关键城池的局部演出；
- 重要人物会面；
- 使者抵达；
- 围城或撤退的短镜头；
- 季节和压力变化；
- 司令部状态变化。

不要因为已经做了 3D，就把每一条消息都扩展成可观看的 3D 场面。多数消息应该仍然由文字、图标、来源和地图证据快速表达。

### 4.6 如果从第一天就拍板 3D

如果制作人明确要求首发必须是 3D，那么建议仍然采用“2D 设计验证、3D 最小实现”的方式：

1. 先用 2D 草图确定信息层级和交互；
2. 再用 Unity 或 Godot 4 3D 建一个极小的 3D 场景；
3. 先实现侧栏、暂停、情报边界和命令确认；
4. 最后才加地形、材质、雾效和演出；
5. 在没有通过可读性测试前，不扩大地图和资产数量。

这样做不是偷偷回到 2D 主线，而是避免 3D 美术先行导致玩法被迫迁就画面。

## 5. 3D 版本必须守住的设计边界

无论选哪一个引擎，都应把下面几条写成项目硬规则。

### 5.1 3D 不能泄露玩家不该知道的事实

不能因为：

- 远处模型被渲染出来；
- 敌军在场景中移动；
- AI 单位的路径可见；
- 阴影或粒子暴露位置；
- 镜头跳转自动对准目标；
- 雾效边缘出现轮廓；

就让玩家获得规则上尚未获得的情报。

### 5.2 3D 不能取代消息流

默认壳仍然是：

- 地图司令部；
- 侧边情报消息流；
- 点开消息才暂停；
- 危机强制暂停并说明理由。

3D 场景可以提供上下文，但不能要求玩家绕着地图寻找消息，也不能让玩家通过“看得见”替代情报来源。

### 5.3 3D 不能让危机暂停变成镜头强制播放

危机触发后可以有短暂的视觉提示，但必须：

- 立即说明暂停原因；
- 让玩家知道触发依据；
- 不自动播放长演出；
- 不把玩家拖入不可跳过的镜头；
- 不在镜头中展示超出已知情报范围的画面；
- 允许玩家回到消息流和证据板下令。

### 5.4 3D 不能把空间操作变成新的行动额度

玩家主动动作不设额度，但这不等于玩家需要在 3D 地图上做大量无意义点击。镜头旋转、缩放、拖拽和检查不应被包装成额外的“操作负担”。

### 5.5 3D 不能让史实感压过信息博弈

五代十国的地理、城池和军政氛围应该服务于：

- 边境压力；
- 路线和联络；
- 信息延迟；
- 权力关系；
- 资源和兵力；
- 错误决策的后果。

如果一个 3D 细节不能帮助玩家理解上述内容，它就应该接受“是否值得制作”的审查。

## 6. 精简待拍板

### 1. 首发形态 — **已拍板：A（2D 后 3D 分支）；UE 不首发**

- **A：2D Godot 4.x + C#，3D 作为后期表现分支（推荐）** ← **已拍板**
- B：一开始就做有限 3D，先做小范围试片
- C：一开始就做完整 3D 地图与演出

**已拍板 A。**主荐仍为 2D；不推翻。只有在制作目标、团队能力和发行卖点都已明确要求 3D 时，才议 B；不建议直接选 C。

### 2. 若坚持首发 3D，选择引擎 — **完整 3D 未选；UE 已排除首发；其余若后开 3D 再议**

- **A：Unity（推荐）**
- B：Godot 4 3D
- C：Unreal Engine ← **已排除首发**

用户未选完整 3D；UE 不首发。若日后开 3D 分支，引擎再议（原推荐仍偏 Unity；小范围克制可议 Godot 4 3D）。

### 3. 3D 的产品定位 — **完整 3D 未选；若后开 3D 再议**

- **A：3D 作为地图氛围和少量重点演出层（推荐）**
- B：3D 作为可自由观察的完整战略世界
- C：3D 作为角色、城池和战事的主要游玩空间

首发按 2D，本题暂搁。若后开 3D，原推荐仍为 A：氛围与少量重点演出层；B、C 会显著扩大范围并易偏离已拍板玩法。
